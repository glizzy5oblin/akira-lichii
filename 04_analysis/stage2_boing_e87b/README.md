# Stage-2 `boing` payload (sha256 e87b4995…5da5f9): static analysis

Static analysis only. Nothing here was run natively. The string recovery executes short snippets inside the Unicorn CPU emulator (no OS, no files, no network).

## What it is
It is the Akira Remote RAT itself, not a separate injector. Comparison with the image rebuilt from `charmap.DMP`:
- Same Go source layout: 794 source files each, 787 file names identical (garble scrambles names per build, so this means the same source and seed). 16,252 functions here against 16,738 in the dump; 3,224 of the ~3,460 recoverable names are common.
- Runtime helpers sit at the same addresses (`runtime.slicebytetostring` 0x140052680, `runtime.newobject` 0x1400153a0), so the emulator and Ghidra scripts from the dump work unchanged on the section ranges below.
- Embedded panel assets: `theme.css` and the second stylesheet are byte-identical to the carved copies. `main_panel.html` and `app.js` are close but not identical (about 560 and 420 bytes shorter), so this is a nearby build, not the same one.
- No embedded second PE, and no plaintext `xmrig`/`randomx` strings (not proof that no miner is carried; it could be fetched or encrypted).

So `boing` is the RAT build the loader fetches, and the injector that hollows `charmap.exe` is code inside it (`0x1403d99c0`, below).

## Recovered strings (`strings_recovered_unique.txt`, `strings_recovered_by_site.tsv`)
`tools/emulate_strings_best.py` decrypts each inline-encrypted literal by emulating its block. It recovered 1,180 printable results out of 5,282 call sites; 837 sites failed and 3,265 results were binary/garbage (misaligned starts). `strings_recovered_unique.txt` keeps the 320 longest printable strings, with substring duplicates dropped. Treat truncated or odd entries as partial.

New in this pass (none of these were in the repo before):
- **Miner launch:** `-o pool.hashvault.pro:443 -u <…> --pass …` (function `0x1405713e0`). Buffers next to it contain `charmap.exe`, so the miner appears to be started with `charmap.exe` as its argv[0]. The wallet/user value was not recovered.
- **Persistence helper `0x1405b5700`:** error strings `Create: regkey failed (DisplayUpdater)` and `Create: all DisplayUpdater.exe mirrors failed`, plus the string `DisplayUpdater.exe`. It writes a registry key and tries several locations for a `DisplayUpdater.exe` copy. The loader's own Run value on the victim is "Microsoft Display Driver Manager"; a quick text search of Roaming, the Python install folder and ProgramData on the mounted disk found no `DisplayUpdater` (the rest of the disk and the registry were not searched).
- **Process injection helper `0x1403d99c0`:** `invalid PE: %v`, `WriteProcessMemory (headers): %v`. A generic "write this PE into a process" routine.
- **Defender tampering `0x140776fc0`** (16 KB): strings `Neutralize engine payload`, `requires elevation`, the `SOFTWARE\Policies\Microsoft\Windows Defender\Real-Time Protection` key, the PowerShell switches `-DisableIntrusionPreventionSystem -DisableCatchupFullScan -DisableRemovableDriveScanning -MAPSReporting`, values `DisableAntiSpyware`, `DisableBehaviorMonitoring`, `DisableIOAVProtection`, the services `WinDefend`, `WdFilter`, `WdNisSvc`, `SecurityHealthService`, and the four Defender scheduled-task names. The string `requires elevation` suggests it only works with admin rights, and the victim's loader ran unelevated (FINDINGS section 10). Whether it ran, or succeeded, was not checked: the Defender 5007 events in the offline logs on and after 11/07 that were skimmed were routine service-start state changes.
- **Panel routes not in the earlier list:** `/api/schtasks/create`, `/api/firewall/rule`, `/api/defender/status`, `/api/reg/keys`, `/api/services`, `/api/tcp`, `/api/sessions`, `/api/files/fetch`, `/api/audio/mic`, `/api/clipboard/{history,clear}`, `/api/cursor`, `/api/quality`, `/api/miner/restart`, `/api/bot/session/{start,stop}`, `/api/bot/vault/{start,import}`, `/api/recovery/autofill`, `/hvnc/restart`, `/ws/term`, `/ws/audio`; hidden-desktop name `akira_hvnc`; environment variable `AKIRA_STORE_DIR`; `akira_bot`.

## Second pass: whole-function emulation (`strings_whole_function_emulation.tsv`, `tools/emu_all.py`, `emu3.py`)
Emulating whole functions (calls faked, buffers dumped) recovered strings the per-site method missed:
- **`0x1405b0a60`** (`pyStartup: mkdir %s: %v`): `LOCALAPPDATA`, `Programs`, `Python399`, `/python3.zip`, `pythonw.exe`. `0x1405b3380` also builds `%LOCALAPPDATA%\Programs\Python399`. So the RAT itself contains the code that creates the fake `Python399` folder and handles `/python3.zip` (a path suffix joined to a base URL or file name). This answers the open question: `python3.zip` is a component the RAT's own startup routine stages, not something the loader's author on the victim created by hand. (The user's own `python.zip` of the Python399 loader folder is a separate, unrelated file.) What base URL it is appended to was not recovered; the mirrors are encrypted.
- **`0x1408441c0`**: `calc.exe tunnel --url http://localhost:%d` and `C:\Windows\System32\calc.exe`. This is the cloudflared launch, with a format-string port (the dump shows 49912). The hollowed host is `calc.exe`; no `cloudflared` or `trycloudflare` string was recovered, so where the binary comes from is still open (likely embedded or fetched as an encrypted URL).
- **`0x1405a76e0`**: `/akgo.php`, `dllhost.exe`, `charmap.exe`, `TerminateProcess`, `CloseHandle`.
- GoFile upload (`0x14038ab80` "UploadGoFile panic: %v", `0x140379c20` `https://api.gofile.io/servers`) and zip-name builders. Decompiled bodies stored in `key_functions_pseudocode/`.
- Dump cross-check: the live `charmap.DMP` strings hold the decrypted lists (six domains, `/well-known/pki-validation/go/{akgo.php,err.php,boing}`) and the message `watchdog: failed to fetch payload from all mirrors`, so the RAT has a watchdog that re-fetches `boing` from the mirror list. The sample has the same code, but its domain strings were **not** decrypted from the sample file; they are known only from the dump.

## Third pass: random-path emulation (`tools/emu_paths.py`, `strings_random_path_*`)
Forward conditional branches were forced randomly (150 seeds on `0x1406f0f60`, 12 seeds on each of the 402 worklist functions) to reach code the straight-line run skips. Result: `0x1406f0f60` is the **browser/app profile table** (Vivaldi, Naver Whale, Yandex, `LocalAppData`, `fa-solid fa-globe`/`fa-brands` icon names), the S-box blocks decrypt but yield browser names, not C2. Across the worklist the only new readable strings were `charmap.exe`, `conhost.exe`, `dllhost.exe`. No domain, URL, `pki-validation`, `cloudflared`, Telegram or mirror string appeared. Two of the ten shards hit the 1,500 s limit and printed nothing (output is written only at the end), so those ~80 functions are not covered. Forcing branches also breaks loops, so many outputs are partial garbage.

## Fourth pass: real helper execution (`tools/emu_init.py`, `strings_init_emulation.txt`)
Most literals are decrypted by small per-string helper functions, so faking every call hides them. `emu_init.py` instead executes helper calls for real inside Unicorn (depth-limited; `duffzero`/`duffcopy` at `0x14006f420`-`0x14006f940` must also run for real, which was the bug that hid the first results) and extracts printable runs from the buffers. 824 functions were run (`strings_init_emulation.txt`, 920 result lines). New results:
- **cloudflared source (function `0x140843920`, called from the launcher `0x1408441c0` through a `sync.Once`):** a 99-byte XOR/add-decrypted string = `https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe`. It is fetched with a Go `net/http` client (300 s timeout), status must be 200, body read with `io.ReadAll`. The 4-byte string at `0x140b63716` is plaintext `.exe`; the function also looks for `.bat`/`.cmd` suffixes. The launcher then runs it as `calc.exe tunnel --url http://localhost:%d` (hollowed host `C:\Windows\System32\calc.exe`). So the `calc.DMP` cloudflared is the stock GitHub release, downloaded by the RAT at run time (the user's own machine would show a GitHub download at that moment; not checked in logs).
- **Mirror list / dead drop (`0x1403b8640`, `0x1403c12a0`, `0x1403c10a0`):** nine BSC JSON-RPC endpoints are in the sample: `bsc.publicnode.com`, `lb.routeme.sh/rpc/evm/56`, `binance.llamarpc.com`, `bsc.api.pocket.network`, `bsc-dataseed1/2/3.defibit.io`, `bsc-dataseed1/2.ninicoin.io`, `rpc.backrunshield.com` (names as recovered; some trailing bytes are junk). The mirrors are therefore **not** hard-coded in the sample: they come from the contract (`get()` selector `0x6d4ce63c`, contract `0xF97CB22B8dBd52790493e962d4684B3FDB08A2Be`). The string returned in the memory dump is decoded here (`onchain_config_payload.bin`, `tools/decode_chain_config.py`): every byte -4, six base64 chunks, each an XZ stream holding one URL. Result (`onchain_config_decoded_urls.txt`): `atomicplanets.cc`, `seaofstar.st`, `cosmicsky.cc`, `waterseas.xyz`, `dpdc737.dpdatacenter.com`, `dongphucasian.com`, each with `/well-known/pki-validation/go/boing`. This is the snapshot held in the dump; the live contract may differ (not queried).
- **`python3.zip` base URL:** `0x1403c10a0` takes a URL and runs `strings.Replace(url, "/boing", suffix, 1)` for every mirror. `pyStartup` (`0x1405b0a60`) calls it with the suffix `/python3.zip` (built by a closure just before the call at `0x1405b0f12`). So the archive is fetched from `<mirror>/well-known/pki-validation/go/python3.zip` on the same six hosts. This URL pattern is inferred from the code; no request was made. The persistence helper `0x1405b5700` calls the same helper with a 16-byte suffix whose text is unknown (`/DisplayUpdater.exe` would be 19 bytes, so it is not simply that name); the suffix is decrypted at `0x1405b5bf8`-`0x1405b6125` (16-byte buffer, byte fix-ups, then a permutation loop) **keyed by a run-time dword**: `[global 0x1411608e8] + 0x1c4` and its high half. That value is not in the file, and the charmap dump holds no matching string, so the suffix cannot be recovered statically. (Straight emulation of the function stops early on its first call; starting past the check at `0x1405b573e` yields only `Create: user.Current: %v`, `Create: pyStartup failed, falling back to DisplayUpdater.exe`, `Create: all DisplayUpdater.exe mirrors failed`.) The fallback message shows `pyStartup` is tried first and `DisplayUpdater.exe` from the mirrors only if it fails.
- **Other plaintext now recovered:** Discord API `https://discord.com/api/v9/users/@me`, `/users/@me/channels`, `/channels/%s/messages`; `http://ip-api.com/json`; `https://api.gofile.io/servers`; Firefox archive name `%s_%s_Firefox.zip`; wallet extension profile folders (e.g. `Local Extension Settings\fnnegphlobjdpkhecapkijjdkgcjhkib`); miner arguments `--donate-level 1 --tls --tls-fingerprint 420c7850e09b7c0bdcf748a7da9eb3647daf8515718f36d9ccfdd6b9ff834b14` after `-o pool.hashvault.pro:443 -u ... --pass`.

## Not found
- No Telegram string and no wallet/miner user string were recovered. The `-u` value is built elsewhere.
- The persistence helper's 16-byte suffix (`0x1405b5700`) depends on a run-time struct field and is not recoverable from the file. `0x140776fc0` aborted after 9 instructions (unmapped read).
- The current on-chain config was not read; only the dump snapshot is decoded. Whether `python3.zip` actually sits at the inferred URL is unverified.
